# app/ — ต้นแบบที่กดได้จริง

ไฟล์เดียวจบต่อหนึ่งหน้าจอ ไม่มี build step

หน้าเข้าสู่ระบบ เวชระเบียน จุดบริการ และผู้ป่วย **คุยกับ REST API จริง** ผ่าน `js/api.js`
จึงต้องเปิดผ่าน `docker compose` ที่พอร์ต 5173 (เปิดไฟล์ตรง ๆ หรือผ่าน `./serve.sh` จะไม่มี API ให้เรียก)
ส่วนหน้าผัง แผนภาพแม่แบบ ผลกระทบ และโต๊ะช่วยเหลือ ยังใช้ข้อมูลผังที่ฝังไว้ตอน `node app/build.mjs`

| ไฟล์ | หน้าจอ | ใช้ทดสอบอะไร |
|---|---|---|
| `login.html` | หน้าแรกของระบบ | เข้าสู่ระบบตามบทบาท แล้วเดินต่อไปหน้าจอของบทบาทนั้น · ผู้ป่วยเข้าด้วยรหัสบนบัตรคิว |
| `patient-mobile.html` | ผู้ป่วย (มือถือ) | อ่านคำสั่งทีละข้อขณะเดิน · ยืนยันตำแหน่งใหม่เมื่อหลง · เปลี่ยนเส้นทางกลางทาง · สลับ 5 ภาษา |
| `registrar.html` | เวชระเบียน (จอคอม) | สามขั้นตอนเมื่อผู้ป่วยมาถึง และผลที่ได้ออกมาคือบัตรคิวกับข้อมูลที่ลงฐานข้อมูล |
| `patient-map.html` | แผนที่ผู้ป่วย | ทีละชั้น เส้นเดียว ซูมเฉพาะช่วงที่กำลังเดิน |
| `station.html` | จอจุดบริการ | คิวจริงของแผนกจาก API · กดแล้วหน้าผู้ป่วยเปลี่ยนตามภายใน 5 วินาที |
| `admin.html` | จัดการระบบ | หน้าแรกของผู้ดูแลระบบหลังเข้าสู่ระบบ · ตรวจผังอัตโนมัติ |
| `impact.html` | ผลกระทบเมื่อปิดเส้นทาง | ปิดลิฟต์หนึ่งตัวกระทบใครเท่าไร · รับรายงานจากผู้ใช้ |
| `map.html` | ผังเส้นทาง | ผังรวมทุกอาคารทุกชั้นพร้อมเส้นทางทั้งวัน และผังรายชั้น |
| `pathway.html` | แผนภาพแม่แบบ | ขั้นตอนการมาหนึ่งครั้งในรูปเดียว พร้อมเงื่อนไขลำดับและกำหนดเวลา |

`registrar.html` สร้าง QR ที่สแกนได้จริง — พิมพ์บัตรแล้วสแกนด้วยมือถือจะเปิดหน้าผู้ป่วยทันที
ช่องล่างสุดของหน้าเปลี่ยนที่อยู่ปลายทางใน QR ได้ ถ้าจะชี้ไปเครื่องที่ใช้สาธิต

## เรื่องภาษา

คำสั่งนำทาง **ไม่ได้เขียนไว้เป็นประโยคตายตัวต่อเส้นทาง** แต่เก็บเส้นทางเป็นข้อมูล (เลี้ยวไหน กี่เมตร ไปจุดไหน)
แล้วประกอบประโยคจากแม่แบบของแต่ละภาษาตอนแสดงผล — โครงเดียวกับที่ `backend/src/domain/instructions.js` ใช้

```js
{ act: 'walk', turn: 'left', m: 24, arrive: 'B3-LAB', side: 'right', hint: 'water' }
```
กลายเป็น "เลี้ยวซ้าย เดิน 24 เมตร ห้องเจาะเลือดอยู่ขวามือ" · "Turn left, walk 24 m, Blood test is on your right" ·
"左转，步行 24 米，抽血室在您右手边" และภาษาอื่นโดยใช้ข้อมูลชุดเดิม

**เพิ่มประเทศใหม่** = เพิ่มหนึ่งรายการใน `LANGS` หนึ่งชุดใน `DICT` (46 ข้อความ) และชื่อห้องใน `PLACES`
ไม่ต้องแตะข้อมูลเส้นทางเลย · ลูกศร ไอคอน และตัวเลขไม่ต้องแปลอยู่แล้ว

ฟอนต์โหลด Noto Sans / SC / Myanmar เสริม Sarabun เพื่อให้จีน เมียนมา และซีริลลิกแสดงผลถูกต้อง
ภาษาแรกที่เปิดมาเดาจากภาษาของเบราว์เซอร์ และจำค่าที่ผู้ใช้เลือกไว้ในเครื่อง

## รูปของแต่ละจุด

ตาราง `node_photos` ในสคีมาเก็บรูปจริงของแต่ละจุด ต้นแบบนี้ทำให้ครบสองทาง

**ภาพจำลอง** — วาดด้วย canvas ตอนรัน ครบทั้ง 30 จุด · 12 ชนิดฉาก

| ฉาก | ใช้กับ |
|---|---|
| เคาน์เตอร์ · ประตูห้อง · ห้องตรวจ · โต๊ะนัดหมาย | เวชระเบียน การเงิน ห้องยา คัดกรอง ประชาสัมพันธ์ ห้องเจาะเลือด เอกซเรย์ อายุรกรรม คลินิกทั่วไป ห้อง 401/403 จุดนัดหมาย |
| ลิฟต์ · บันได · ทางลาด · ทางเชื่อม | ลิฟต์ A/B/C และโถงลิฟต์ · บันได A/B · ทางลาด C · ทางเชื่อมทุกจุด |
| ที่นั่งรอ · ห้องน้ำ · ทางเข้าหลัก · ตู้เอทีเอ็ม | จุดพักคอย · ห้องน้ำทั้ง 4 ชั้น · ประตูทางเข้า · ตู้เอทีเอ็มข้างร้านกาแฟ |

ป้ายเหนือจุดใช้สีเดียวกับ `departments.color` และเขียนชื่อตามภาษาที่เลือก
ทุกภาพติดป้าย **"ภาพจำลอง · illustration"** ไว้ในตัวภาพเอง เพื่อไม่ให้เข้าใจผิดว่าเป็นรูปถ่ายจริงของโรงพยาบาล

**รูปถ่ายจริง** — กด "ถ่ายรูปจุดนี้" เปิดกล้องมือถือได้ทันที ระบบย่อเหลือด้านยาว 1000 px แล้วเก็บไว้ในเครื่อง
ภาพที่ถ่ายเองจะขึ้นป้ายเขียว "รูปจริงของจุดนี้" แทน และลบออกได้

**เลือกตำแหน่งด้วยรูป** — แผ่น "ตอนนี้คุณอยู่ตรงไหน" เป็นตารางรูป ไม่ใช่รายการตัวหนังสือ
คนที่หลงและอ่านภาษาไม่ออกกดรูปที่ตรงกับสิ่งที่เห็นได้เลย · จุดที่คนมักยืนอยู่ 8 จุดขึ้นก่อน
และทุกจุดในกลุ่มนั้นมีเส้นทางเขียนไว้ครบ กดแล้วได้คำสั่งเต็มทันที

**หน้ารวมรูป** — กด "รูปทุกจุดในโรงพยาบาล" ในแผ่นรูปหรือในแผงเดโม เพื่อดูทุกจุดเรียงตามอาคารและชั้น
จุดที่มีรูปถ่ายจริงแล้วจะมีจุดเขียวกำกับ

เดินถ่ายสถานที่จริงหน้างานแล้วรูปขึ้นในแอปทันที โดยไม่ต้องแก้โค้ด — ในระบบจริงรูปเหล่านี้ไปอยู่ที่
`node_photos` และนำเข้าล่วงหน้าผ่าน `data/node-photos.csv` ได้

## ผังเส้นทาง (`map.html`)

ไม่ใช่รูปภาพ — หน้านี้สร้างจาก `data/nodes.csv` (พิกัด `map_x`, `map_y`) และ `data/edges.csv`
และ **คำนวณเส้นทางด้วย Dijkstra ในหน้านั้นจริง ๆ** ด้วยกติกาเดียวกับ `backend/src/domain/graph.js`
ไม่ได้วาดเส้นทิ้งไว้ล่วงหน้า

| มุมมอง | เห็นอะไร |
|---|---|
| **ภาพรวมทั้งโรงพยาบาล** | ทุกจุดทั้ง 50 จุดและ 8 ชั้นอยู่ในรูปเดียว ฉายเอียงแบบผังมหาวิทยาลัย อาคารซ้อนขึ้นตามชั้นและมีผนังด้านหน้าให้เห็นความหนา |
| **ตัดขวางทุกชั้น** | ภาพตัดขวางทั้ง 3 อาคาร ชั้นล่างอยู่ล่าง ชั้นบนอยู่บน · เส้นทางทั้งวัน 7 ขั้นลากทับ · เส้นแนวตั้งคือลิฟต์ บันได ทางลาด · เส้นระหว่างอาคารคือทางเชื่อม |
| **รายชั้น** | ผังพื้นของชั้นนั้นพร้อมชื่อทุกจุด |

ปุ่ม **♿ รถเข็น** และ **🛗 ปิดลิฟต์ B** เปลี่ยนเส้นทางบนแผนที่ทันที — ปิดลิฟต์ B แล้วรถเข็นจะอ้อมไปทางลาดอาคาร C
ส่วนคนเดินใช้บันได B ซึ่งเป็นสถานการณ์ 2.3 ในเอกสารออกแบบ คำนวณสดไม่ได้เขียนไว้ล่วงหน้า

กดหมุดหรือรายการขั้นตอนด้านขวาเพื่อดูเฉพาะช่วงนั้น

## แผนภาพแม่แบบ (`pathway.html`)

แผนภาพของ **การมาโรงพยาบาลหนึ่งครั้ง** ทั้งชุดในรูปเดียว วาดจาก `data/pathways.csv`

จุดสำคัญคือ **ไม่ได้เรียงเป็นเส้นตรง** แต่จัดคอลัมน์ตามเงื่อนไขลำดับ (`prereq_steps`)
ขั้นที่อยู่คอลัมน์เดียวกันคือขั้นที่ไม่ผูกเงื่อนไขกันและสลับก่อนหลังได้ — ซึ่งเป็นช่องที่ระบบใช้
ยกขั้นที่มีกำหนดเวลาขึ้นมาก่อน เช่นแม่แบบ DM-FU ที่ "ชั่งน้ำหนัก" กับ "เจาะเลือด" อยู่คอลัมน์เดียวกัน
ระบบจึงส่งผู้ป่วยไปเจาะเลือดก่อนได้เมื่อใกล้ 11:00

กล่องเส้นประคือช่วงรอ กรอบสีส้มคือขั้นที่มีกำหนดเวลา เส้นสีหลักคือจุดที่หลายขั้นมารวมกัน

### สร้างหน้าที่งอกจากข้อมูลใหม่

```bash
node app/build.mjs              # อ่าน data/*.csv แล้วเขียน app/map.html และ app/pathway.html
TEMPLATE=WALKIN node app/build.mjs
```

แก้พิกัดใน `nodes.csv` แล้วรันใหม่ แผนที่เปลี่ยนตามทันที ไม่ต้องแก้โค้ดหน้าเว็บ
วันไหนได้ภาพผังจริงของโรงพยาบาลมา วางเป็นพื้นหลังแล้วปักหมุดด้วยพิกัดชุดเดิมได้เลย


## แผนที่ผู้ป่วย (`patient-map.html`) ต่างจากผังผู้ดูแลระบบยังไง

ซึ่งเป็นข้อมูลที่ผู้ป่วยที่กำลังรีบอ่านไม่ไหว `patient-map.html` จึงตัดข้อมูลทิ้งเป็นหลัก

| หลักที่ยืมมาจากแอปนำทาง | ทำยังไงในนี้ |
|---|---|
| ทีละหน้าจอ ไม่ใช่ทั้งเส้นทาง | ตัดเส้นทางเป็น "ช่วง" ทีละชั้น รอยต่อคือลิฟต์ บันได ทางลาด หรือทางเชื่อม |
| ซูมตามช่วงที่กำลังเดิน | คำนวณกรอบจากจุดในช่วงนั้นแล้วตั้ง viewBox ให้พอดี |
| เส้นทางเด่น อย่างอื่นจาง | ทางเดินอื่นบนชั้นเดียวกันวาดสีจาง จุดสังเกตใส่ไอคอนเล็ก |
| การ์ดบอกทีละเลี้ยวด้านล่าง | ระยะทาง จำนวนเลี้ยว และป้ายบอกว่าต้องขึ้นลิฟต์ไปชั้นไหนต่อ |
| แถบความคืบหน้า | ขีดหนึ่งขีดต่อหนึ่งช่วง เห็นว่าเหลืออีกกี่ช่วง |
| ตัวเลือกชั้น | แสดงเฉพาะชั้นที่เส้นทางนี้ผ่าน ไม่ใช่ทุกชั้นในโรงพยาบาล |

**สิ่งที่ทำไม่ได้** — จุดที่ขยับตามตัวผู้ป่วยแบบ GPS ในอาคารทำไม่ได้จริง
ความคลาดเคลื่อน 5–20 เมตรและแยกชั้นไม่ได้ ต้องติดอุปกรณ์ในอาคารถึงจะทำได้
ระบบนี้จึงใช้ตำแหน่งที่ยืนยันแล้วจากเจ้าหน้าที่หรือ QR ที่ผนังแทน และวาดจุด "คุณอยู่ตรงนี้" ที่จุดเริ่มของแต่ละช่วง

ชื่อห้องในฐานข้อมูลมีแค่ไทยกับอังกฤษ ภาษาอื่นจึงแสดงชื่อห้องเป็นอังกฤษ ส่วนคำสั่งนำทางแปลครบทั้ง 5 ภาษา


## ผลกระทบเมื่อปิดเส้นทาง (`impact.html`)

เจ้าหน้าที่ที่กดปิดลิฟต์เพื่อซ่อมบำรุงมองไม่เห็นว่ากำลังทำอะไรกับใคร เพราะตัวเองเดินบันไดได้
หน้านี้คำนวณให้ดูก่อนตัดสินใจ โดยเทียบระยะทางก่อนปิดกับหลังปิดของทุกคู่จุดบริการ แยกตามโปรไฟล์ผู้ป่วย

ตัวเลขจากผังชุดปัจจุบัน:

| ปิดอะไร | คนเดิน | ผู้ใช้รถเข็น |
|---|---|---|
| ลิฟต์ B (ชั้น 2↔3) | +8 ม. | **+203 ม.** (25 เท่า) |
| ลิฟต์ A (ชั้น 1↔2) | +6 ม. | **ไปไม่ถึงเลย 32 เส้นทาง** |
| ทางเชื่อม A→B | ไม่กระทบ | **ไปไม่ถึงเลย 30 เส้นทาง** |
| ลิฟต์ C (ชั้น 3↔4) | ไม่กระทบ | **ไปไม่ถึงเลย 14 เส้นทาง** |
| บันได A และ B | ไม่กระทบ | ไม่กระทบ (รถเข็นใช้บันไดไม่ได้อยู่แล้ว) |

หน้าจอยังบอกด้วยว่าตอนนี้มีผู้ป่วยรายไหนกำลังใช้เส้นทางนั้นอยู่ (`data/active-visits.csv`)
และในจำนวนนั้นใช้รถเข็นกี่ราย ก่อนกดยืนยันปิดและแจ้งเตือน

### แจ้งเส้นทางชำรุดจากผู้ใช้

หน้าแผนที่ผู้ป่วยมีปุ่ม **"แจ้งเส้นทางมีปัญหา"** เลือกได้ว่าแจ้งทางขึ้นลงชั้นหรือทางเดินช่วงนั้น
พร้อมเหตุผล 6 แบบ (ลิฟต์เสีย · ปิดซ่อม · มีของขวาง · พื้นลื่น · ประตูล็อก · อื่น ๆ) ครบทั้ง 5 ภาษา

รายงานจะไปโผล่ที่หน้าผู้ดูแลระบบทันที เรียงตามจำนวนครั้งที่ถูกแจ้ง กดแล้วดูผลกระทบได้เลย
จุดที่ถูกแจ้งซ้ำคือจุดที่ควรดูก่อน

ต้นแบบส่งรายงานผ่านที่เก็บข้อมูลในเบราว์เซอร์ เพื่อให้สาธิตข้ามแท็บได้ทันทีโดยไม่ต้องมีเซิร์ฟเวอร์
ระบบจริงยิงเป็น `POST /api/reports` แล้วเข้าคิวให้เจ้าหน้าที่ยืนยันก่อนปิดเส้นทางจริง


## หน้าจัดการระบบ (`admin.html`)

ผู้ดูแลระบบเข้าสู่ระบบแล้วลงที่นี่ ไม่ใช่กระโดดเข้าฟีเจอร์ใดฟีเจอร์หนึ่ง

- **ตัวเลขสรุป** จำนวนจุด เส้นทาง แม่แบบ ผู้ป่วยที่กำลังเดินอยู่ และจุดที่ถูกแจ้งว่ามีปัญหา
- **แถบเตือน** ขึ้นทันทีเมื่อมีผู้ใช้แจ้งเส้นทางมีปัญหา พร้อมลิงก์ไปดูผลกระทบ
- **เมนูจัดการ** ทุกส่วนของระบบ โดยติดป้ายตามความจริง — `ภาพนิ่ง` สำหรับหน้าที่ยังเป็น mockup
  และ `ยังไม่ได้ทำ` สำหรับผู้ใช้/สิทธิ์ บันทึกการใช้งาน และตัวจำลองสถานการณ์ ซึ่งกดไม่ได้
- **ตรวจผังอัตโนมัติ** เดินกราฟจริงจากประตูทางเข้าหลักทุกครั้งที่เปิดหน้า

ผลตรวจของผังชุดปัจจุบัน:

| ข้อตรวจ | ผล |
|---|---|
| จุดบริการที่เดินไปไม่ถึง | ✅ ไม่มี |
| จุดบริการที่รถเข็นไปไม่ถึง | ✅ ไม่มี |
| จุดที่รถเข็นเข้าไม่ได้ | ℹ️ 5 จุด — เป็นบันไดทั้งหมด ซึ่งถูกต้อง |
| จุดที่เข้าได้แต่ออกไม่ได้ | ℹ️ บันไดหนีไฟ B — ลงทางเดียวโดยตั้งใจ |

สองข้อหลังเป็นข้อมูลไม่ใช่ข้อผิดพลาด ระบบจึงแยกสีไว้ — ถ้ามีห้องตรวจหลุดมาอยู่ในรายการนั้นแปลว่าผังผิดจริง


## จอจุดบริการ (`station.html`) — จุดที่ระบบเชื่อมกันจริง

เดิมการสาธิต "เจ้าหน้าที่กดเสร็จ แล้วขั้นถัดไปเด้งขึ้นมือถือผู้ป่วย" ใช้ปุ่มจำลองในหน้าผู้ป่วยเอง
ซึ่งพิสูจน์อะไรไม่ได้ ตอนนี้เป็นของจริงสองหน้าจอ

**ท่าสาธิต**

1. เปิด `station.html` บนแท็บเล็ตหรือหน้าต่างหนึ่ง เลือกแผนก **ห้องเจาะเลือด**
2. เปิด `patient-mobile.html` บนมือถือหรืออีกหน้าต่าง
3. ที่จอจุดบริการกด **✋ มาถึง → 📣 เรียก → ✔ เสร็จ**
4. หน้าผู้ป่วยเปลี่ยนเป็นขั้นถัดไปเอง สั่นเตือน และขึ้นข้อความว่าเจ้าหน้าที่อัปเดตให้

เจ้าหน้าที่กดปุ่มเดียวต่อครั้ง ระบบบันทึกเวลาให้เอง ไม่ต้องกรอกอะไร และ **บังคับลำดับสถานะ**
เหมือนที่ API จะทำ — กดเรียกก่อนมาถึงไม่ได้ กดเสร็จก่อนเรียกไม่ได้ ถ้าสถานะถูกเปลี่ยนจากอีกจอแล้ว
จะขึ้นเตือนแทนที่จะเขียนทับ

ปุ่ม **➕ ส่งตรวจเพิ่ม** แทรกขั้นเอกซเรย์ก่อนชำระเงิน แล้วแผนของผู้ป่วยเปลี่ยนทันทีทั้งสองจอ

### สถานะที่ใช้ร่วมกัน

ต้นแบบเก็บ visit ไว้ที่ `carepath.visit` ในเบราว์เซอร์ ทั้งสองหน้าอ่านเขียนที่เดียวกัน
และฟัง `storage` event เพื่ออัปเดตข้ามแท็บทันที พร้อมถามซ้ำทุก 4 วินาทีเป็นตาข่ายรองรับ

ระบบจริงคือตาราง `visit_steps` โดยจอจุดบริการเรียก `PATCH /api/visit-steps/:id/status`
และหน้าผู้ป่วยถาม `GET /api/p/:token` ทุก 5 วินาที — พฤติกรรมที่เห็นเหมือนกัน ต่างแค่ที่เก็บข้อมูล

ตรวจแล้วว่าเดินได้ครบทั้ง 7 ขั้นจนจบ รวมกรณีแทรกเอกซเรย์กลางทาง และทุกขั้นมีแผนกรับผิดชอบครบ
