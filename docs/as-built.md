# CarePath — เอกสารระบบตามที่สร้างจริง

บันทึกย้อนหลังว่าระบบที่ส่งมอบ *เป็นอย่างไรจริง ๆ* ไม่ใช่ตามที่ออกแบบไว้ตอนต้น
เขียนหลังงานเสร็จ เพื่อให้คนที่มารับช่วงต่ออ่านแล้วทำงานต่อได้โดยไม่ต้องเดา

---

## 1. สรุปหนึ่งย่อหน้า

CarePath บอกผู้ป่วยตลอดวันว่า **ตอนนี้ต้องไปที่ไหน และไปยังไง** โดยคำนวณเส้นทางจากผังโรงพยาบาล
ที่เก็บเป็นข้อมูล ปรับตามความต้องการพิเศษของแต่ละคน และจัดลำดับขั้นตอนให้ทันเวลาที่แพทย์กำหนด
เจ้าหน้าที่แต่ละจุดกดปุ่มเดียวแล้วขั้นถัดไปเด้งขึ้นมือถือผู้ป่วยเอง

**สถานะ** ต่อครบทั้งสามชั้นบนเครื่องแล้ว — Next.js → NestJS → PostgreSQL
หน้าหลักสี่หน้า (เข้าสู่ระบบ เวชระเบียน จุดบริการ ผู้ป่วย) ทำงานกับข้อมูลจริงในฐานข้อมูล
ยังไม่ได้ยกขึ้น Cloudflare — เลือกลงทุนกับความครบของระบบก่อน เหตุผลอยู่ท้ายหัวข้อถัดไป

## 2. สถาปัตยกรรมตามที่เป็นจริง

```
เบราว์เซอร์ ──▶ Next.js :5173 ──┬── หน้า React 4 หน้า + ไฟล์นิ่งใน public/
                                └── /api/ ──▶ NestJS :3000 ──▶ PostgreSQL :5432
```

ทั้งสามชั้นเป็นคนละ container ใน `docker-compose.yml` — `web` · `api` · `db`
เบราว์เซอร์เห็นแค่พอร์ต 5173 พอร์ตเดียว Next.js เป็นคน proxy `/api/` ต่อให้ ไม่มีหน้าไหนต่อฐานข้อมูลเอง

หน้าเว็บทุกหน้าเรียก API ผ่าน `frontend/lib/api.ts` ไฟล์เดียว — ที่เดียวที่รู้จักรูปร่างของ API
token ของเจ้าหน้าที่อยู่ใน sessionStorage ของแท็บ ส่วนผู้ป่วยใช้ token ที่อยู่ในลิงก์ของบัตรคิว

ฝั่ง API แบ่งเป็นเจ็ดโมดูลตามพื้นที่งาน (`auth · map · catalog · visits · patient · stations · admin`)
สิทธิ์ตรวจด้วย `AuthGuard` + `@Roles()` ที่ API เสมอ หน้าจอซ่อนปุ่มไม่ถือเป็นการป้องกัน
ตรรกะโดเมน (Dijkstra · topological sort · ประโยคนำทาง) เป็นฟังก์ชันล้วน ทดสอบได้โดยไม่ต้องมีฐานข้อมูล

หน้าผัง แผนภาพแม่แบบ ผลกระทบ โต๊ะช่วยเหลือ และหน้าจัดการระบบ ยังเป็น HTML นิ่งใน
`frontend/public/` ที่ใช้ข้อมูลผังฝังตอน build (`node app/build.mjs`) เพราะเป็นภาพนิ่งของผัง
ซึ่งไม่เปลี่ยนระหว่างวัน — ขั้นถัดไปคือให้หน้าเหล่านี้ดึงจาก `GET /api/map` แทน

**ลิงก์เดิมยังใช้ได้** — บัตรคิวที่พิมพ์ไปแล้วชี้มาที่ `patient-mobile.html?t=…`
Next.js redirect ไป `/patient?t=…` ให้เอง QR เก่าจึงยังสแกนได้

**เหตุผลที่ยังไม่ขึ้น Cloudflare** — หน้าเว็บขึ้นได้ (เป็น client component ล้วน ไม่มี server action)
แต่ API ขึ้นตรง ๆ ไม่ได้ ติดหกจุด: Nest ผูกกับ Express adapter ซึ่ง Workers ไม่มี · bcrypt rounds 10
กิน CPU 60–100 ms เกินโควตา 10 ms ของแผนฟรี · `pg.Pool` ต้องผ่าน Hyperdrive · `fs.readFile`
สำหรับ schema และ CSV ไม่มีบน Workers · แคชกราฟกับนาฬิกาจำลองไม่แชร์ข้าม isolate
รายละเอียดและทางแก้รายข้ออยู่ใน `README.md` หัวข้อข้อจำกัด — ตัดสินใจรันครบทั้งกองบนเครื่องก่อน

## 5. อัลกอริทึมที่ใช้จริง

**เส้นทาง** Dijkstra บนกราฟ 105 ทิศทาง น้ำหนักเป็นวินาที
`cost = walk_seconds × (รถเข็นหรือผู้สูงอายุ ? 1.5 : 1)` และตัดเส้นที่ `is_accessible = false`
ออกทั้งหมดเมื่อเป็นรถเข็น — เขียนซ้ำในทุกหน้าที่ต้องใช้ ด้วยกติกาเดียวกับ `backend/src/domain/graph.js`

**ลำดับขั้น** เงื่อนไข `prereq` ทำให้แผนเป็นกราฟ ไม่ใช่รายการ ขั้นที่อยู่คอลัมน์เดียวกันสลับกันได้
ระบบเลือกขั้นที่ใกล้ที่สุดก่อน ยกเว้นเมื่อขั้นที่มีกำหนดเวลาจะไม่ทัน จึงยกขั้นนั้นขึ้นมาก่อน

**การแบ่งช่วงของแผนที่ผู้ป่วย** ตัดเส้นทางทุกครั้งที่เปลี่ยนชั้นหรือเปลี่ยนอาคาร
หนึ่งช่วงคือหนึ่งหน้าจอ รอยต่อกลายเป็นป้าย "ขึ้นลิฟต์ไปชั้น 3"

## 7. บันทึกการตัดสินใจ

| ตัดสินใจอะไร | ทำไม |
|---|---|
| ผังเป็น CSV ไม่ใช่รูปภาพ | โรงพยาบาลย้ายห้องทุกปี รูปภาพล้าสมัยทันทีและต้องจ้างวาดใหม่ |
| ไม่ใช้ภาพผังของที่อื่นมาดัดแปลง | เป็นงานของผู้อื่น และกรรมการคือคนที่รู้ผังจริง |
| เขียนกำกับทุกหน้าว่าเป็นผังสาธิต | ผิดพลาดเรื่องผังหน้ากรรมการจะทำลายความน่าเชื่อถือทั้งระบบ |
| ภาพประกอบไม่ติดป้ายว่าเป็นภาพถ่ายจริง | ตัวหนังสือบนป้ายในภาพเพี้ยน แสดงว่าเป็นภาพที่ AI สร้าง |
| แผนที่ผู้ป่วยแยกจากผังผู้ดูแลระบบ | ผังรวม 50 จุด 8 ชั้นอ่านไม่ไหวสำหรับคนกำลังรีบ |
| ไม่ทำตู้คีออส | ผู้ใช้ยกเลิกระหว่างทาง จึงถอดออกทั้งหมดไม่ทิ้งเศษไว้ |
| สถานะร่วมผ่านที่เก็บในเบราว์เซอร์ | สาธิตสองหน้าจอเชื่อมกันได้จริงโดยไม่ต้องมีเซิร์ฟเวอร์ |
| ยังไม่ย้าย API ขึ้น Workers | ติด 3 จุดที่พังแบบเงียบ ไม่ใช่ error ชัด เสี่ยงเกินไปก่อนเดโม |

## 8. ข้อจำกัดที่รู้ตัว

- **ผังเป็นชุดสมมุติ** ไม่ใช่ผังจริงของโรงพยาบาลวชิระภูเก็ต
- **ไม่มีการระบุตำแหน่งอัตโนมัติ** ในอาคาร GPS คลาดเคลื่อน 5–20 เมตรและแยกชั้นไม่ได้
  ระบบใช้ตำแหน่งที่เจ้าหน้าที่ยืนยันหรือผู้ป่วยกดบอกแทน
- **ปุ่มสแกน QR ผนังยังไม่ต่อกล้องจริง** แต่ผังมี `qr_token` เตรียมไว้แล้ว 26 จุด
- **ชื่อห้องในฐานข้อมูลมีแค่ไทยกับอังกฤษ** ภาษาอื่นจึงแสดงชื่อห้องเป็นอังกฤษ
- **เส้นทางในต้นแบบเขียนไว้ 15 คู่** จุดอื่นได้คำสั่งรวบข้อเดียว — ของจริงไม่มีข้อจำกัดนี้
  เพราะ Dijkstra คำนวณได้ทุกคู่

## 9. วิธีรันและเผยแพร่

```bash
# ทั้งระบบ: หน้าเว็บ + API + ฐานข้อมูล
cp .env.example .env
docker compose up -d --build              # db :5433 · api :3000 · web :5173
docker compose exec api npm run reset     # สร้างตารางและนำเข้าข้อมูลตัวอย่าง
open http://localhost:5173/login

# เทสต์และตัวตรวจ SQL รันบนเครื่อง ไม่ใช่ในคอนเทนเนอร์
# (image ของ api ตัด devDependencies ออก จึงไม่มี jest อยู่ข้างใน)
cd backend
npm install
npx jest              # 24 กรณี
npm run lint:sql      # ทุก query ต้องเป็น parameterized
cd ..

# หน้าที่งอกจากข้อมูลผัง (ผัง แผนภาพแม่แบบ ผลกระทบ โต๊ะช่วยเหลือ จัดการระบบ)
# เขียนทั้งใน app/ และ frontend/public/
node app/build.mjs
```

**สาธิตจากมือถือ** — เปิดหน้าเว็บด้วย IP ของเครื่องแทน localhost
(`ipconfig getifaddr en0`) แล้ว QR บนบัตรคิวจะฝังที่อยู่นั้นให้เองอัตโนมัติ
