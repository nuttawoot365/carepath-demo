1. โจทย์และขอบเขต

1.1 ปัญหาจากหน้างาน

ผู้ป่วยนอกของโรงพยาบาลขนาดใหญ่ต้องผ่านหลายจุดบริการในหนึ่งวัน — เวชระเบียน คัดกรอง เจาะเลือด รอผล พบแพทย์ ชำระเงิน รับยา — โดยแต่ละจุดอยู่คนละอาคารคนละชั้น ปัญหาที่เกิดซ้ำทุกวันคือ

  • ผู้ป่วยไม่รู้ว่า ตอนนี้ต้องไปที่ไหนต่อ เพราะใบนัดบอกแค่รายการ ไม่ได้บอกลำดับหรือเส้นทาง
  • ป้ายบอกทางออกแบบสำหรับคนที่รู้ผังอยู่แล้ว ผู้สูงอายุและผู้ใช้รถเข็นเดินผิดทางแล้วต้องย้อนกลับ
  • เจ้าหน้าที่ต้องตอบคำถามเดิมซ้ำทั้งวัน แทนที่จะได้ทำงานของตัวเอง
  • แรงงานต่างชาติและนักท่องเที่ยวอ่านป้ายภาษาไทยไม่ออก

1.2 สิ่งที่ระบบต้องทำ (Functional)

#ความต้องการผู้ใช้
F1เปิดการมาโรงพยาบาลหนึ่งครั้ง (visit) จากแม่แบบขั้นตอน พร้อมออกบัตรคิวที่มี QRเวชระเบียน
F2บอกผู้ป่วยว่าขั้นถัดไปคืออะไร อยู่ที่ไหน และเดินไปยังไงทีละข้อผู้ป่วย
F3คิดเส้นทางตามความต้องการพิเศษ — รถเข็นต้องไม่เจอบันไดผู้ป่วย
F4เจ้าหน้าที่จุดบริการเปลี่ยนสถานะขั้นตอนด้วยปุ่มเดียว แล้วหน้าผู้ป่วยเปลี่ยนตามเองจุดบริการ
F5แทรกขั้นตอนระหว่างวันได้ (แพทย์สั่งตรวจเพิ่ม) แล้วจัดลำดับใหม่ให้ถูกต้องจุดบริการ
F6ปิดเส้นทางได้ (ลิฟต์ซ่อม) แล้วคำนวณทางใหม่และแจ้งผู้ป่วยที่กระทบผู้ดูแลระบบ
F7ดูผลกระทบก่อนตัดสินใจปิดเส้นทาง — ใครเดินเพิ่มเท่าไร ใครไปไม่ถึงผู้ดูแลระบบ
F8ค้นผู้ป่วยด้วยเลขคิวเมื่อเดินหลงมาถาม แล้วยืนยันตำแหน่งให้ประชาสัมพันธ์

1.3 สิ่งที่ระบบต้องเป็น (Non-functional)

#ข้อกำหนดวิธีที่ทำให้เป็นจริง
N1ผู้ป่วยไม่ต้องติดตั้งแอปและไม่ต้องสมัครสมาชิกเว็บล้วน · เข้าด้วย token ในลิงก์ของบัตรคิว
N2เจ้าหน้าที่ต้องเสียเวลาเพิ่มไม่เกิน 2 วินาทีต่อผู้ป่วยหนึ่งคนปุ่มเดียวต่อหนึ่งสถานะ ไม่มีฟอร์มให้กรอก
N3รองรับผู้ที่อ่านไทยไม่ออก5 ภาษา — ไทย อังกฤษ จีน เมียนมา รัสเซีย
N4รองรับผู้ที่ไม่มีมือถือบัตรกระดาษพิมพ์คำสั่งเดินละเอียดขึ้น · เจ้าหน้าที่ยืนยันตำแหน่งแทน
N5ผังจริงของโรงพยาบาลต้องนำเข้าได้โดยไม่ต้องแก้โค้ดผังทั้งหมดอยู่ใน CSV และฐานข้อมูล ไม่มีที่ไหน hard-code
N6ข้อมูลผู้ป่วยต้องตรวจสอบย้อนหลังได้และแก้ไม่ได้ตาราง audit append-only · REVOKE UPDATE, DELETE
N7ฐานข้อมูลต้องเป็น PostgreSQL และอยู่ในรูป 3NF17 ตาราง · ทุก query เป็น parameterized

1.4 ขอบเขต MVP

อยู่ในขอบเขต — การมาโรงพยาบาลของผู้ป่วยนอกหนึ่งวัน ตั้งแต่ยื่นบัตรถึงรับยา · บทบาทผู้ใช้ 4 แบบ (เวชระเบียน จุดบริการ ผู้ดูแลระบบ ผู้บริหาร) · ผังสมมุติ 3 อาคาร 50 จุด

นอกขอบเขต — ผู้ป่วยใน · การนัดหมายล่วงหน้า · การเชื่อมกับ HIS ของโรงพยาบาล · การชำระเงินจริง · แอปมือถือ

2.2 เหตุผลของการแยกชั้น

การตัดสินใจเหตุผล
Frontend กับ Backend แยกกันจริง คุยผ่าน REST เท่านั้น เป็นข้อกำหนดของโจทย์ และทำให้เปลี่ยนฝั่งใดฝั่งหนึ่งได้โดยไม่กระทบอีกฝั่ง — พิสูจน์แล้ววันที่ 2 ตอนเปลี่ยนทั้งสองฝั่งคนละรอบ
Next.js เป็นคน proxy /api แทนที่จะให้เบราว์เซอร์ยิงตรง เบราว์เซอร์เห็น origin เดียว จึงไม่ต้องตั้ง CORS และไม่ต้องเปิดพอร์ต API ออกสู่ภายนอก
ตรรกะโดเมนเป็นฟังก์ชันล้วน แยกจาก controller และฐานข้อมูล ทดสอบอัลกอริทึมได้โดยไม่ต้องมีฐานข้อมูล — เทสต์ 24 กรณีรันเสร็จใน 9 วินาที
สถานะทั้งหมดอยู่ในฐานข้อมูล ไม่มีใน session ของเซิร์ฟเวอร์ จอจุดบริการกับหน้าผู้ป่วยอ่านความจริงชุดเดียวกัน จึงไม่มีทางเห็นไม่ตรงกัน

2.3 การซิงก์ระหว่างสองหน้าจอ

3. การออกแบบฐานข้อมูล

3.1 แนวคิดหลัก — ผังโรงพยาบาลคือกราฟ

การตัดสินใจที่สำคัญที่สุดของโครงการคือ เก็บผังเป็นกราฟ ไม่ใช่รูปภาพ ทุกจุดในโรงพยาบาลเป็นโหนด (nodes) ทุกทางเดิน ลิฟต์ บันได ทางลาด ทางเชื่อม เป็นเส้นเชื่อมมีทิศทาง (edges) พร้อมระยะทาง เวลาเดิน ทิศเลี้ยว และ ธงว่ารถเข็นผ่านได้หรือไม่

ผลคือการหาเส้นทางกลายเป็นปัญหา shortest path ธรรมดา และการรองรับรถเข็น กลายเป็นแค่การตัด edge ที่ is_accessible = false ออกจากกราฟ โดยไม่ต้องเขียนตรรกะพิเศษแยก

3.4 การตัดสินใจที่ควรอธิบาย

เรื่องทำไมออกแบบแบบนี้
แยก template_steps ออกจาก visit_steps ตอนเปิด visit ระบบ คัดลอก ขั้นตอนจากแม่แบบมาเป็นของ visit นั้น ถ้าผู้ดูแลแก้แม่แบบตอนบ่าย ผู้ป่วยที่เปิดบัตรตอนเช้าต้องไม่ถูกเปลี่ยนแผนกลางคัน
prereqs เป็น N:N วนตัวเอง ไม่ใช่คอลัมน์ after_step ขั้นหนึ่งอาจต้องรอหลายขั้น เช่น "พบแพทย์" ต้องรอทั้งเจาะเลือดและเอกซเรย์ ตารางเชื่อมจึงเป็นรูปเดียวที่ไม่บังคับให้ลำดับเป็นเส้นตรง
visit_steps.service_point_id ชี้ไป nodes ไม่ snapshot ชื่อห้อง ถ้าห้องย้าย ผู้ป่วยที่ยังเดินอยู่ต้องถูกพาไปห้องใหม่ ไม่ใช่ห้องเก่าที่จดไว้
edges มีทิศทาง บันไดหนีไฟเดินลงได้อย่างเดียว · ทางเดินที่เลี้ยวซ้ายขามา ต้องเลี้ยวขวาขากลับ ตอนนำเข้า CSV ที่มี bidirectional=1 ระบบสร้างสองแถวและสลับซ้ายขวาให้เอง
visits.token 32 ตัวอักษร + short_code 8 ตัว token อยู่ใน QR สำหรับสแกน · short_code พิมพ์ใต้ QR สำหรับคนที่กล้องเสียหรือบัตรเปียก ใช้ตัวอักษรที่อ่านไม่สับสน (ตัด I O 0 1 ออก)
ไม่เก็บเลขบัตรประชาชน ระบบไม่ต้องใช้ จึงไม่เก็บ — ลดความเสียหายถ้าข้อมูลรั่ว

4. การนอร์มัลไลเซชัน

ฐานข้อมูลอยู่ในรูป 3NF ทั้งหมด ตรวจทีละระดับ

4.1 1NF — ทุกช่องเก็บค่าเดียว

ไม่มีคอลัมน์ไหนเก็บรายการคั่นด้วยจุลภาค ตัวอย่างที่ล่อใจที่สุดคือ "ขั้นนี้ต้องรอขั้นไหนบ้าง" ซึ่งถ้าทำง่าย ๆ จะกลายเป็น prereq = "1;3;4" — เราแยกเป็นตาราง visit_step_prereqs หนึ่งแถวต่อหนึ่งเงื่อนไขแทน

หมายเหตุ: visits.profile เป็น JSONB เก็บธงความต้องการพิเศษ ซึ่งเป็นการยกเว้นที่ตั้งใจ — ธงเหล่านี้ไม่มีความสัมพันธ์กับตารางอื่นและไม่เคยถูก query แยกรายธง ระบบตรวจค่าที่รับเข้าให้เหลือเฉพาะธงที่รู้จัก 4 ตัวก่อนบันทึกเสมอ

4.2 2NF — ไม่มีคอลัมน์ที่ขึ้นกับคีย์แค่บางส่วน

ตารางที่มีคีย์ประกอบคือตาราง prereqs ทั้งสองตัว ซึ่งมีแค่สองคอลัมน์ที่เป็นคีย์ทั้งคู่ จึงไม่มีคอลัมน์อื่นให้ขึ้นกับคีย์บางส่วนได้

4.3 3NF — ไม่มีคอลัมน์ที่ขึ้นกับคอลัมน์ที่ไม่ใช่คีย์

จุดที่ต้องระวังคือโซ่ อาคาร → ชั้น → แผนก → จุด ถ้าออกแบบแบบง่าย ตาราง nodes จะมีคอลัมน์ building และ floor อยู่ในตัวเอง ซึ่งทำให้ชื่ออาคารถูกเก็บซ้ำ 50 ครั้ง และถ้าเปลี่ยนชื่ออาคารต้องไล่แก้ทุกแถว

เราแยกเป็นสามตารางแทน nodes เก็บแค่ floor_id ส่วนชั้นรู้ว่าตัวเองอยู่อาคารไหน ผลคือ

  • เปลี่ยนชื่ออาคารแก้แถวเดียว มีผลทุกหน้าจอทันที
  • ไม่มีทางเกิดสภาพที่จุดสองจุดบอกว่าอยู่ชั้น 3 อาคาร B แต่คนละแผนกกันแบบขัดแย้ง

ตัวอย่างการสืบย้อนในของจริง

SELECT n.code, n.name_th, d.code AS dept, f.level AS floor, b.code AS building
  FROM nodes n
  JOIN floors f     ON f.id = n.floor_id
  JOIN buildings b  ON b.id = f.building_id
  LEFT JOIN departments d ON d.id = n.department_id
 WHERE n.is_active;

ทุกหน้าจอที่ต้องแสดง "อาคาร B ชั้น 3" ใช้ join ชุดนี้ ไม่มีที่ไหนเก็บสตริงสำเร็จรูปไว้

6. อัลกอริทึมที่เป็นหัวใจ

6.1 หาเส้นทาง — Dijkstra ที่รู้จักความต้องการพิเศษ

ต้นทุนของแต่ละ edge ไม่ใช่ระยะทางคงที่ แต่คิดจากโปรไฟล์ผู้ป่วย

function costFor(profile) {
  const slower = (profile.elderly || profile.wheelchair) ? 1.5 : 1;

  return (edge) => {
    if (profile.wheelchair && !edge.is_accessible) return Infinity;   // ตัดออกจากกราฟ

    let seconds = edge.walk_seconds * slower;
    if (profile.elderly && edge.kind === 'stairs') seconds += 60;     // บันไดคือภาระจริง
    if (profile.has_phone === false && edge.turn && edge.turn !== 'straight') seconds += 5;
    return seconds;                                   // ไม่มีมือถือ = ทุกทางเลี้ยวเสี่ยงหลง
  };
}

คืนค่า Infinity แทนการลบ edge ออกจริง ทำให้ใช้กราฟชุดเดียวกับทุกคนได้ โดยไม่ต้องสร้างกราฟใหม่ต่อผู้ป่วยหนึ่งราย

ผลที่พิสูจน์ด้วยเทสต์

สถานการณ์ผลที่ระบบเลือก
คนเดินปกติ จากทางเข้าไปห้องแล็บเลือกบันได 44 วินาที เพราะเร็วกว่าลิฟต์
ผู้ใช้รถเข็น เส้นทางเดียวกันเลี่ยงบันได ไปทางลิฟต์ ใช้เวลามากกว่า
ผู้สูงอายุ เส้นทางเดียวกันเส้นทางเดิมแต่เวลามากขึ้นตามตัวคูณ
ปิดลิฟต์แล้วผู้ใช้รถเข็นไปไม่ถึงคืน null และขึ้นคำเตือน ไม่ใช่เส้นทางที่เดินไม่ได้

6.2 เลือกขั้นถัดไป — ไม่ใช่แค่เรียงตามลำดับ

ขั้นถัดไปไม่ได้เลือกจากเลขลำดับอย่างเดียว แต่จากสามเงื่อนไขซ้อนกัน

  1. ทำได้ตอนนี้ไหม — ขั้นที่ต้องทำก่อนต้องเสร็จหรือถูกข้ามหมดแล้ว
  2. มีกำหนดเวลาที่กำลังจะไม่ทัน — ถ้าเดินไปถึงแล้วทำเสร็จเกิน (กำหนด − 20 นาที) ระบบยกขั้นนั้นขึ้นมาก่อนแม้จะเดินไกลกว่า
  3. ถ้าไม่มีอะไรเร่ง ก็เลือกที่เดินใกล้ที่สุด — ลำดับเดิมเป็นตัวตัดสินเมื่อเสมอกัน

ตัวอย่างจริง: ผู้ป่วยเบาหวานต้องเจาะเลือดก่อน 11:00 น. ถ้าเปิดบัตร 10:40 น. ระบบจะพาไปเจาะเลือดก่อน แม้ว่าจุดคัดกรองจะอยู่ใกล้กว่า และแสดงเหตุผลให้ผู้ป่วยเห็นบนหน้าจอ

6.3 แทรกขั้นกลางวัน — Topological Sort (Kahn)

เมื่อแพทย์สั่งตรวจเพิ่ม ขั้นใหม่ต้องไปอยู่ตำแหน่งที่ถูกต้องโดยไม่มีใครระบุเอง

1. แทรกขั้นใหม่ด้วยลำดับกึ่งกลาง  (ก่อน "ชำระเงิน" ลำดับ 6 → ได้ 5.5)
2. บันทึกเงื่อนไข: เอกซเรย์ต้องทำหลัง "พบแพทย์"
3. เรียงใหม่ทั้งแผนด้วย Kahn's algorithm  (ลำดับเดิมเป็นตัวตัดสินเมื่อเลือกได้หลายขั้น)
4. ถ้าเรียงไม่ครบ = เงื่อนไขวนกลับมาหากันเอง → ปฏิเสธด้วย 422 PREREQ_CYCLE
5. เขียนลำดับ 1..n กลับลงฐานข้อมูลในทรานแซกชันเดียวกัน

ผลจริงที่รันวันนี้ — เอกซเรย์ถูกวางเป็นลำดับที่ 6 หลัง พบแพทย์ (ลำดับ 5) และ ก่อน ชำระเงิน (ลำดับ 7) โดยไม่มีใครบอกตำแหน่ง

6.4 ประโยคนำทาง — ข้อมูลล้วน ไม่ใช่ข้อความสำเร็จรูป

ระบบไม่เก็บประโยค "เลี้ยวขวาแล้วเดิน 24 เมตร" ไว้ในฐานข้อมูล แต่เก็บเป็นข้อมูล { turn: 'right', m: 24, to: 'LIFT-B' } แล้วประกอบเป็นประโยคตอนแสดงผลตามภาษาที่เลือก การเพิ่มภาษาที่ 6 จึงเป็นการเพิ่มชุดคำแปล ไม่ต้องแตะข้อมูลเส้นทางเลย

ทางเดินตรงที่ต่อเนื่องกันถูกยุบเป็นข้อเดียวและรวมระยะทาง เพื่อไม่ให้ผู้ป่วยต้องอ่าน 12 ข้อ สำหรับทางเดินเส้นเดียว

6.5 ผลกระทบก่อนปิดเส้นทาง

ก่อนผู้ดูแลระบบกดปิดลิฟต์ ระบบคำนวณให้ดูก่อนว่ากระทบใครบ้าง โดย จำลองการปิดบนกราฟสำเนา ไม่แตะฐานข้อมูล แล้วเทียบจำนวนจุดที่ไปถึงได้ และเวลารวมที่ต้องใช้ ระหว่างคนเดินปกติกับผู้ใช้รถเข็น

10.1 สิ่งที่ตัดสินใจทำและทำไม

Sprint 4 และ 5 ของวันที่ 2 คือ Backend Implementation และ Frontend Implementation ทีมเลือกใช้ช่วงนี้ ยกระดับ stack ทั้งสองฝั่งเป็นเฟรมเวิร์กมาตรฐานอุตสาหกรรม แทนที่จะเพิ่มฟีเจอร์ใหม่ เพราะ

  • TypeScript จับความผิดพลาดของรูปข้อมูลระหว่าง front กับ back ได้ตั้งแต่ตอนคอมไพล์

เงื่อนไขที่ตั้งไว้ก่อนเริ่ม — ฐานข้อมูลห้ามแตะ · API contract ห้ามเปลี่ยน · ลิงก์เดิมที่พิมพ์ลงบัตรคิวไปแล้วต้องยังใช้ได้ · ถ้าทำไม่เสร็จก่อนพักเที่ยงให้ย้อนกลับทั้งหมด

12.2 ทำไมยังไม่ขึ้น Cloudflare Workers

หน้าเว็บขึ้นได้ทันที เพราะทั้ง 4 หน้าเป็น client component ไม่มี server action แต่ API ขึ้นตรง ๆ ไม่ได้ ติด 6 จุด

#จุดปัญหา
1NestJS HTTP adapterผูกกับ Express ซึ่ง Workers ไม่มี · ต้องเปลี่ยนเป็น Hono
2bcrypt rounds 10ใช้ CPU 60–100 ms เกินโควตา 10 ms ของแผนฟรี
3pg.Poolต้องต่อผ่าน Hyperdrive และใช้ Postgres ภายนอก
4fs.readFileอ่าน schema และ CSV ตอน reset · Workers ไม่มีระบบไฟล์
5แคชกราฟผังเก็บในหน่วยความจำของ instance ไม่แชร์ข้าม isolate
6นาฬิกาจำลองเหตุผลเดียวกับข้อ 5 · ตั้งแล้วเครื่องอื่นไม่เห็น

ทีมเลือกลงทุนเวลากับความครบและความถูกต้องของระบบก่อน แล้วสาธิตจากเครื่องผ่านเครือข่ายภายใน ซึ่งพิสูจน์การทำงานจริงได้ครบเท่ากัน

12.3 ถ้ามีเวลาต่อ

  1. เขียน API ใหม่เป็น Hono แล้วขึ้น Workers พร้อม Postgres บน Neon ผ่าน Hyperdrive
  2. ให้หน้าที่ยังเป็น HTML นิ่งดึงจาก GET /api/map เพื่อให้ผังเปลี่ยนแล้วเห็นทันทีทุกหน้า
  3. นำผังจริงของโรงพยาบาลเข้าระบบผ่าน CSV แล้ววัดผลกับผู้ป่วยจริง
  4. เพิ่มหน้าจัดการผู้ใช้ หน้าดู audit และระบบ backup
